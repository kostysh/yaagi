# Модули, BDD и планы

- Document ID: `project.methodology.modules`

## Модуль

Модуль — ограниченная способность системы с наблюдаемым поведением. Он не определяется папкой, техническим слоем или набором низкоуровневых функций.

Модуль должен:

- поддерживать конкретную часть концепции;
- иметь понятную публичную границу;
- быть независимо проверяемым;
- скрывать внутреннюю реализацию;
- допускать изменение внутреннего устройства без переписывания требований.

## Спецификация модуля

До разработки очередного модуля применяется [правило связи документов](documentation.md#правило-связи-документов): системный дизайн должен описывать всю целевую систему. Из него берутся роль модуля, поставщики входов, потребители результатов, общие гарантии и участие в сборках. Спецификация уточняет этот вклад на публичной границе.

Спецификация фиксирует только то, что нужно для реализации и приёмки:

- назначение и связь с концепцией, архитектурой и потоками системного дизайна;
- границы и явные non-goals;
- публичный контракт;
- наблюдаемое поведение, включая существенные ошибки;
- состояние и инварианты, если они важны;
- применимые ограничения качества;
- критерии приёмки.

Для каждого существенного входа и результата указывается соответствующий участник системного потока. Проверки модуля и его вклад в сквозную приёмку описываются раздельно: двойник публичного порта не подтверждает совместную работу реальной сборки. Изменение взаимодействия сначала согласуется в системном дизайне и его вышестоящих источниках, если затрагивает их решения.

Требования не описывают внутренние классы, функции или последовательность вызовов. Используется [шаблон спецификации](templates/module-specification.md).

## BDD

BDD используется для обсуждения и фиксации поведения на границе модуля.

- Сценарий формулируется как `Дано / Когда / Тогда` на языке предметной области.
- Помимо основного пути фиксируются только значимые отказ и восстановление.
- Gherkin и отдельный BDD-фреймворк не обязательны.
- Исполняемыми BDD-тестами становятся критические сценарии, для которых это снижает риск расхождения между спецификацией и кодом.
- Unit-тесты не требуется переписывать в BDD-форму.

## План имплементации

Для каждого модуля создаётся один компактный [план имплементации](templates/module-implementation-plan.md). Он содержит задачи, зависимости, возможные параллельные потоки, точки интеграции и проверки.

Инкремент связывается с нужной сборкой системного дизайна: какую возможность он открывает, какие реальные соседи необходимы и где проверяется их совместная работа. Порядок между модулями остаётся в roadmap.

План не повторяет спецификацию и не проектирует реализацию до уровня функций. Задача должна давать проверяемый результат и обычно завершаться одним обозримым PR.

Параллельная работа разрешается, когда публичные контракты уже определены. Общая изменяющаяся граница означает последовательную работу, а не искусственный параллелизм.

## Алгоритмы

Отдельное [описание алгоритма](templates/algorithm.md) создаётся только для нетривиальной логики, где важны инварианты, завершение, сложность или специальные пограничные случаи. Очевидная логика объясняется кодом и тестами.
