# Методика задач

- Document ID: `project.methodology.task-methodology`

Этот документ задаёт постановку, статусы, зависимости и сдачу задач. Правила веток, worktree, публикации и операций GitHub находятся в [Git и GitHub](git-and-github.md).

## Поток задачи

1. Выбрать Issue со статусом `Ready`.
2. Создать task-ветку и worktree от актуальной `origin/develop` по [Git workflow](git-and-github.md#ветки-и-worktree).
3. Перевести Issue в `In progress`.
4. Выполнить задачу по спецификации и плану, провести проверки и аудиты.
5. В пределах разрешения оператора опубликовать task-ветку и создать PR в `develop`.
6. Перевести Issue в `In review`.
7. После merge перевести Issue в `Done` и удалить локальный worktree.

При внешней блокировке Issue переводится в `Blocked` с кратким описанием условия продолжения. После снятия блокировки задача возвращается в `Ready` или `In progress` по фактическому состоянию.

## GitHub Project и Issues

GitHub Project использует одно поле статуса:

`Backlog → Ready → In progress → In review → Done`

`Blocked` — боковой статус для задачи, которая не может продолжаться.

Для имплементации модуля создаётся одна рамочная Issue. Она содержит ссылки на спецификацию и план модуля по мере их подготовки. Крупные задачи соответствуют модулям, сборкам и экспериментам дизайна. Sub-issues нужны только при полезном выделении самостоятельного проверяемого результата из плана; каждый пункт плана отдельной Issue не становится. Рамочная Issue может охватывать несколько инкрементов и PR.

Issues являются навигационными: краткое описание требуемого результата связывает работу с точными разделами проектных документов. Полные требования, BDD-сценарии, контракты и план в карточку не переносятся. При расхождении источником истины остаются проектные документы.

### Стандарт описания задачи

**Статус: предложен 2026-10-01, ожидает согласования оператором.** До согласования этой редакции описания существующих Issues не переписываются. Предложение охватывает также уточнения о крупности задач и кратком описании результата в двух абзацах выше.

Issue должна быть понятной точкой входа для исполнителя без истории чата. Из её тела должно быть ясно, какой модуль или этап требуется разработать либо проверить, где прочитать точные требования и как сдать результат. Навигационный характер задачи не означает, что вместо постановки достаточно списка ссылок.

Задача определяет, что выполнить и как сдать результат. Последовательность реализации, алгоритмы и предписания по внутреннему устройству в её тело не включаются. План выполнения ведётся отдельным документом; согласованные контракты и ограничения читаются в нормативных источниках по ссылкам.

Заголовок имеет вид `<модуль или этап>: <результат>`. Тело явно называет тот же модуль, сборку или эксперимент; заголовок не заменяет это указание.

Тело содержит четыре коротких раздела:

1. **Что сделать.** Назвать объект работы, требуемое действие и наблюдаемый результат в нескольких предложениях. Для модуля указать его назначение и нужную сборку, для интеграции или эксперимента — проверяемый результат. Существенные границы указать кратко; внутренние функции и будущие расширения не придумывать.
2. **Требования.** Дать ссылки на конкретные разделы документов, задающих работу: для модуля — спецификации, для сборки или эксперимента — соответствующих разделов дизайна и критериев проверки; при необходимости — архитектуры или концепции. На существующий план можно сослаться для навигации, сохраняя шаги выполнения в самом плане. У каждой ссылки указать, какое решение, поведение или критерий там искать. Ссылка на весь документ допустима только для короткого документа, целиком относящегося к задаче. До подготовки спецификации и плана модуля явно указать их отсутствие и принятые исходные разделы; не ссылаться на будущий файл как на действующий источник требований.
3. **Зависимости.** Указать необходимые входные результаты и связанные Issues. Для поэтапной сборки назвать нужный инкремент предшественника: закрытие всей его рамочной Issue не требуется, если достаточно принятого промежуточного результата. Зависимости задают условия начала работы, а не шаги её выполнения; ожидание будущей очереди не превращает весь бэклог в `Blocked`.
4. **Приёмка и сдача.** Указать ожидаемый пакет, документы или evidence и их место в репозитории; кратко назвать решающую проверку со ссылкой на критерии приёмки. До начала соответствующего инкремента назвать конкретные обязательные проверки и виды аудита по [правилам качества](quality.md#ci) и [политике аудитов](audits.md#выбор-аудита); для дополнительных проверок кратко указать риск или условие, на котором основан их выбор. Если исходные требования, план или правила поставки требуют проверки после merge, указать её и ожидаемое подтверждение. Сдача проходит через PR в `develop`; права на публикацию и merge остаются в пределах разрешения оператора.

Ожидаемые критерии приёмки и фактическое подтверждение выполнения указываются раздельно внутри раздела «Приёмка и сдача». При постановке задачи задаются критерии и проверки; по ходу выполнения добавляется ссылка на итоговый PR с проверенным commit, результатами проверок/CI, verdict аудитов и evidence. Подтверждения, которых нет в PR, связываются отдельными ссылками. Для незавершённых проверок явно отмечается, что осталось проверить; они не считаются успешными. Для рамочной Issue подтверждение относится к указанному инкременту; всю Issue закрывают по правилам ниже. Отрицательные отчёты сохраняются по [политике аудитов](audits.md#результаты-и-отчёты).

Глубина описания соответствует готовности работы. Для `Backlog` достаточно понятного результата, исходных требований и явных пробелов готовности: например, отсутствующей спецификации или зависимости. Перед `Ready` для реализации модуля должны быть готовы принятые спецификация и план; для сборки или эксперимента — соответствующие исходные требования и сценарии проверки. Нужные контракты и зависимости должны быть доступны, критерии приёмки и сдачи выбранного инкремента — понятны. Спецификации всех будущих модулей заранее не требуются.

Порядок работ читается в [роадмэпе](../roadmap.md#последовательность); у строки этапа должна быть прямая ссылка на его Issue, когда она создана. В самой Issue остаются зависимости и ссылки на источники, в Project — оперативный статус. Промежуточный PR закрывает рамочную Issue только если весь её заявленный объём принят; иначе он ссылается на неё без автоматического закрытия.

Перед созданием или обновлением описания проверить: модуль или этап назван в теле, ожидаемый результат понятен, ссылки ведут к нужным разделам, условия старта и сдачи не требуют угадывания. Если смысл задачи можно понять только после чтения всей концепции или истории обсуждения, описание нужно уточнить. Для реализации исполнитель всё равно читает указанные нормативные разделы.

Используется [компактный шаблон delivery Issue](templates/delivery-issue.md). Он задаёт форму описания, а не отдельную спецификацию или новый источник требований.
