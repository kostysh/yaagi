# Проектные документы

- Document ID: `project.methodology.documentation`

## Иерархия источников истины

Документы образуют короткую иерархию:

1. `docs/polyphony_concept.md` — каноническая концепция и границы проекта.
2. `docs/architecture.md` и `docs/adr/` — архитектура и отдельные значимые решения.
3. [Системный дизайн](../system-design.md) — совместное функционирование всех модулей целевой системы; разрабатывается по [методологии системного дизайна](system-design.md).
4. `docs/modules/<module-id>/specification.md` — требуемое поведение модуля.
5. `docs/modules/<module-id>/implementation-plan.md` — задачи и порядок имплементации модуля.
6. `docs/modules/<module-id>/algorithms/` — только существенные алгоритмические решения.
7. Код и тесты — реализация и доказательства поведения.

Вышестоящий документ имеет приоритет. Нижестоящий документ не может молча изменить его смысл: конфликт сначала разрешается на соответствующем уровне.

GitHub Issues и элементы GitHub Project не входят в эту иерархию. Они содержат краткое описание требуемого результата, ссылки на его источники и статус, но не копируют полные требования или план. Их постановка и ведение описаны в [методике задач](task-methodology.md); статус согласования предлагаемого [стандарта описания задачи](task-methodology.md#стандарт-описания-задачи) указан в самом стандарте.

[Дорожная карта реализации](../roadmap.md) определяет общий порядок модулей, экспериментов и точек интеграции на основе архитектуры и системного дизайна и содержит [сводку состояния разработки](../roadmap.md#состояние-разработки). Статус в сводке относится к явно указанному объёму инкремента/этапа и подтверждается ссылками на приёмку или PR. Оперативные статусы задач, review и блокировки остаются в Issues/Project. Корневой README кратко описывает текущие возможности и ссылается на сводку.

Roadmap не вводит и не переопределяет требования: перед разработкой очередного модуля создаются его спецификация и компактный план на основе принятого системного дизайна. Изменение зависимости или результат эксперимента обновляет roadmap в той же работе; изменение архитектурного решения сначала отражается в архитектуре.

## Правило связи документов

Каждый уровень имеет собственный предмет:

| Документ | Что определяет | Что передаёт следующему уровню |
| --- | --- | --- |
| Концепция | Назначение, обязательные способности и границы системы | Требуемое целостное поведение |
| Архитектура и ADR | Состав и границы модулей, владельцев, допустимые зависимости и общие ограничения | Принятые решения для совместной работы |
| Системный дизайн | Как все модули обеспечивают способности системы: взаимодействия, потоки, состояние, обратные связи и состав проверяемых сборок | Роль каждого модуля в потоках и обязательства на его публичной границе |
| Спецификация модуля | Точное поведение и публичный контракт в рамках системных взаимодействий | Критерии реализации и приёмки модуля |
| План модуля | Задачи, зависимости и проверки реализации | Проверяемые инкременты и точки интеграции |
| Roadmap | Общую последовательность и состояние поставки | Порядок подготовки модулей, экспериментов и сборок |

Системный дизайн относится к архитектурному уровню и уточняет принятые архитектуру и ADR. Изменение их решений сначала согласуется в соответствующем источнике. Спецификация связывает свои входы, результаты и интеграционную приёмку с конкретными потоками дизайна; план — с соответствующей сборкой. Roadmap ссылается на эти сборки и не подменяет их описание порядком задач.

Каждое решение подробно описывается в одном источнике. Если поток уже задан в архитектуре, системный дизайн связывает его с остальной системой ссылкой и кратким пояснением. Перенос подробного описания сопровождается заменой прежнего текста ссылкой в той же работе; две независимые нормативные копии не поддерживаются. Точные поля контрактов остаются в спецификациях владельцев.

До продолжения разработки модулей подготавливается системный дизайн всей целевой системы. Его текущая версия проходит [аудит](audits.md) и принимается оператором; фиксируются версия и основание принятия. Наличие этой методологии, шаблона или частичного дизайна следующего модуля не закрывает условие. Подробные спецификации всех модулей заранее не требуются.

Проектный документ находится в [docs/system-design.md](../system-design.md); его статус и основание принятия фиксируются в нём самом. Подготовка дизайна не означает, что система реализована.

## Идентификаторы документов

Политика принята оператором 2026-09-28. Канонические проектные документы получают стабильный `Document ID` по схеме:

`<owner>.<kind>[.<local-id>]`

- `<owner>` — `project` для общепроектного документа или стабильный `module-id`;
- `<kind>` — вид документа;
- `<local-id>` — дополнительный идентификатор только для повторяемого вида документа.

Все части записываются в lowercase ASCII. Составные слова разделяются дефисом, уровни идентификатора — точкой.

| Документ | Document ID | Канонический путь |
| --- | --- | --- |
| Концепция | `project.concept` | `docs/polyphony_concept.md` |
| Архитектура | `project.architecture` | `docs/architecture.md` |
| Системный дизайн | `project.system-design` | `docs/system-design.md` |
| Дорожная карта | `project.roadmap` | `docs/roadmap.md` |
| Раздел методологии | `project.methodology.<topic>` | `docs/development-methodology/<topic>.md` |
| ADR | `project.adr.<NNN>` | `docs/adr/ADR-<NNN>-<slug>.md` |
| Спецификация модуля | `<module-id>.spec` | `docs/modules/<module-id>/specification.md` |
| План имплементации | `<module-id>.plan` | `docs/modules/<module-id>/implementation-plan.md` |
| Алгоритм | `<module-id>.algorithm.<algorithm-id>` | `docs/modules/<module-id>/algorithms/<algorithm-id>.md` |
| Отчёт аудита | `<module-id>.validation.<task-id>.<scope-id>.<N>` | `docs/validation/<module-id>/<task-id>.<scope-id>.<N>.md` |

`module-id` — короткий смысловой kebab-case идентификатор. Он назначается при фиксации модуля в архитектуре и после принятия не меняется вместе с названием. `project` зарезервирован как `module-id` для общепроектной области. При разделении или объединении модулей старые ID не переиспользуются; новые границы получают новые ID.

Номер ADR в ID повторяет номер в существующем имени файла: например, `project.adr.001` для `ADR-001-module-boundaries.md`. Принятие политики не требует переименования ADR или изменения действующих ссылок.

Для validation-отчётов:

- `<task-id>` имеет вид `gh-<issue-number>` при наличии реальной delivery Issue. Для методологической задачи без Issue используется стабильный `local-<task-slug>`, например `local-rethink`; Issue только ради имени отчёта не создаётся. После появления Issue первоначальный ID сохраняется, а ссылка добавляется отдельно. Локальный ID задачи в плане имплементации остаётся независимым;
- `<scope-id>` имеет вид `<artifact-scope>-<audit-kind>`, например `spec-concept`, `plan-spec`, `code-security` или `methodology-audits-concept`;
- `<N>` — последовательный номер отрицательного результата для одной комбинации `module-id`, `task-id` и `scope-id`, начиная с `1`.

Правила стабильности:

- заголовок, статус, дата и версия не входят в ID;
- переименование или перемещение файла не меняет ID;
- ID не переиспользуется после замены или удаления документа;
- заменённый документ сохраняет свой ID и получает ссылку `Superseded by`;
- канонический русский документ использует основной ID, а английский перевод — суффикс `.en` и ссылку на канонический ID;
- `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, навигационные страницы и шаблоны отдельных ID не требуют.

В новом документе ID указывается сразу после заголовка. Существующий документ получает ID при следующем значимом изменении; отдельная массовая миграция не требуется.

## Минимальная синхронизация

В одном PR с изменением обновляется только действительно затронутый уровень:

- изменение принципа — концепция и зависимые документы;
- изменение архитектурной границы или решения — архитектура/ADR, затронутые части системного дизайна и спецификации;
- уточнение системного взаимодействия в принятых границах — системный дизайн и затронутые спецификации; состав или порядок сборок также отражается в roadmap;
- изменение поведения модуля — его спецификация и план; при влиянии на других участников сначала согласуется соответствующий системный поток;
- изменение только способа реализации — код, тесты и при необходимости план.

Изменение состояния инкремента/этапа или ближайшего шага обновляет сводку roadmap в том же PR: дата и база среза, завершённый объём, статус и подтверждение. До merge текущий инкремент отмечается «На приёмке»; при следующем обновлении уже слитые PR сверяются и отмечаются «Интегрирован». Этот статус требует проверенного merge в `develop`; evidence применимых проверок, аудитов и CI и исторические ограничения указываются в подтверждении. Обязательные gates текущей поставки сохраняются по [политике качества](quality.md) и [аудитов](audits.md). README обновляется, если изменилось краткое описание доступных возможностей.

Для исправлений формулировок, ссылок и опечаток пересмотр зависимых документов не нужен.

## Язык

- Корневой `README.md` ведётся только на английском языке.
- Общие инструкции агентам в корневом `AGENTS.md` ведутся на английском языке; проектная политика агентов остаётся русскоязычным документом методологии.
- Документация разработки создаётся на русском языке.
- Имена API, типов, команд и другие технические идентификаторы сохраняются без перевода.
- Англоязычные версии остальных документов создаются только по прямому запросу оператора.
- При наличии перевода каноническая версия должна быть указана явно.
