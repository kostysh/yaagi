# Git и GitHub

- Document ID: `project.methodology.git-and-github`

## Ветки и worktree

- Любые изменения репозитория, включая документацию и конфигурацию, проходят путь `отдельный worktree и task-ветка → Pull Request → интеграция в develop`.
- Коммиты изменений выполняются только в task-ветке своего worktree, а не напрямую в `develop` или `master`.
- `develop` — default branch и основная ветка интеграции; принимает PR из любой рабочей ветки.
- `master` — стабильная ветка; PR в неё допускается только из `develop`.
- Прямые push и force push в `develop` и `master` запрещены.
- Создавать, публиковать, перемещать или удалять Git-теги можно только по прямому запросу оператора. Merge и выбор стабильного baseline сами по себе не разрешают создание или публикацию тега.
- Для изменения runtime или persistent state до merge должен быть понятен и проверяем путь отката.
- Каждая задача выполняется в отдельной task-ветке и отдельном worktree.
- Все worktree размещаются в корневом каталоге `.worktree/`, который добавлен в `.gitignore`.
- Корневой `.env` хранит локальное окружение оператора и не коммитится. В каждом worktree `.env` — симлинк на этот корневой файл.
- Связанный `.env` считается общим и read-only для задач; изменяет его только оператор в корне репозитория.
- Один worktree обслуживает только одну задачу.

Типовой локальный старт:

```bash
git fetch origin develop
git worktree add .worktree/<task> -b <task-branch> origin/develop
ln -s ../../.env .worktree/<task>/.env
```

После создания worktree нужно проверить, что симлинк разрешается в корневой `.env`. Секреты и локальные значения из `.env` не копируются в worktree и не коммитятся.

После merge и проверки результата worktree удаляется штатной командой Git, а завершённая локальная task-ветка — обычным безопасным удалением.

Локальные commits, необходимые для стабильного снимка аудита и исправлений, входят в разрешённую оператором задачу. Они не дают дополнительных прав на push, PR, merge, переписывание истории или удаление несведённых изменений. Для этих действий используется уже данное разрешение оператора в пределах его scope; отдельное повторное согласование не требуется.

## Параллельная работа агентов

Делегированием управляет основной агент по [политике агентов](agent-policy.md). Каждый пишущий помощник получает явный write set и владельца результата. Аудиторы и исследователи работают read-only на указанном snapshot. Помощники не публикуют изменения, не выполняют merge и не останавливают чужие ресурсы.

Одна задача сохраняет один task-worktree; внутри него параллельные записи допустимы только в независимые write sets. Общие файлы, lockfile, migrations и локальные ресурсы изменяются последовательно, если безопасное разделение не доказано. Независимая задача получает собственную task-ветку и worktree по обычному процессу.

Перед checkpoint координатор дожидается завершения помощников, проверяет состояние через доступный readback и освобождает принадлежащие задаче ресурсы. Если клиент поддерживает закрытие помощника, используется оно; отсутствие такой операции не заменяется утверждением, что `interrupt` освободил слот. Незавершённые, грязные или явно оставленные для продолжения worktree сохраняются и перечисляются в отчёте.

## Поток задачи

1. Выбрать Issue со статусом `Ready`.
2. Создать task-ветку и worktree от актуальной `origin/develop`.
3. Перевести Issue в `In progress`.
4. Выполнить задачу по спецификации и плану, провести проверки и аудиты.
5. Опубликовать task-ветку и создать PR в `develop`.
6. Перевести Issue в `In review`.
7. После merge перевести Issue в `Done` и удалить локальный worktree.

При внешней блокировке Issue переводится в `Blocked` с кратким описанием условия продолжения. После снятия блокировки задача возвращается в `Ready` или `In progress` по фактическому состоянию.

## GitHub Project и Issues

GitHub Project использует одно поле статуса:

`Backlog → Ready → In progress → In review → Done`

`Blocked` — боковой статус для задачи, которая не может продолжаться.

Для имплементации модуля создаётся одна рамочная Issue. Она содержит ссылки на спецификацию и план модуля по мере их подготовки. Крупные задачи соответствуют модулям, сборкам и экспериментам дизайна. Sub-issues нужны только при полезном выделении самостоятельного проверяемого результата из плана; каждый пункт плана отдельной Issue не становится. Рамочная Issue может охватывать несколько инкрементов и PR.

Issues являются навигационными: краткое описание требуемого результата связывает работу с точными разделами проектных документов. Полные требования, BDD-сценарии, контракты и план в карточку не переносятся. При расхождении источником истины остаются проектные документы.

### Стандарт описания задачи

**Статус: предложен 2026-10-01, ожидает согласования оператором.** До согласования этой редакции описания существующих Issues не переписываются. Предложение охватывает также уточнения о крупности задач и кратком описании результата в двух абзацах выше.

Issue должна быть понятной точкой входа для исполнителя без истории чата. Из её тела должно быть ясно, какой модуль или этап требуется разработать либо проверить, где прочитать точные требования и как сдать результат. Навигационный характер задачи не означает, что вместо постановки достаточно списка ссылок.

Заголовок имеет вид `<модуль или этап>: <результат>`. Тело явно называет тот же модуль, сборку или эксперимент; заголовок не заменяет это указание.

Тело содержит четыре коротких раздела:

1. **Что сделать.** Назвать объект работы, требуемое действие и наблюдаемый результат в нескольких предложениях. Для модуля указать его назначение и нужную сборку, для интеграции или эксперимента — проверяемый результат. Существенные границы указать кратко; внутренние функции и будущие расширения не придумывать.
2. **Требования.** Дать ссылки на конкретные разделы документов, задающих работу: для модуля — спецификации и задач плана, для сборки или эксперимента — соответствующих разделов дизайна и критериев проверки; при необходимости — архитектуры или концепции. У каждой ссылки указать, какое решение, поведение или критерий там искать. Ссылка на весь документ допустима только для короткого документа, целиком относящегося к задаче. До подготовки спецификации и плана модуля явно указать их отсутствие, принятые исходные разделы и необходимость подготовки документов; не ссылаться на будущий файл как на действующий источник требований.
3. **Зависимости и следующий шаг.** Указать необходимые результаты и связанные Issues, затем ближайшее действие исполнителя. Для поэтапной сборки назвать нужный инкремент: закрытие всей рамочной Issue предшественника не требуется, если достаточно принятого промежуточного результата. Такая зависимость не превращает весь будущий бэклог в `Blocked`.
4. **Результат и сдача.** Указать ожидаемый пакет, документы или evidence и их место в репозитории; кратко назвать решающую проверку со ссылкой на критерии приёмки. Обозначить передачу результата через PR в `develop`, применимые [проверки качества](quality.md#ci) и [аудиты](audits.md#выбор-аудита). В PR фиксируются проверенный commit, результаты проверок, verdict аудитов и ссылки на evidence; отрицательные отчёты хранятся по [политике аудитов](audits.md#результаты-и-отчёты). Права на публикацию и merge остаются в пределах разрешения оператора.

Глубина описания соответствует готовности работы. Для `Backlog` достаточно понятного результата, исходных требований и честного следующего шага. Перед `Ready` для реализации модуля должны быть готовы принятые спецификация и план; для сборки или эксперимента — соответствующие исходные требования и сценарии проверки. Нужные контракты и зависимости должны быть доступны, критерии приёмки и сдачи выбранного инкремента — понятны. Спецификации всех будущих модулей заранее не требуются.

Порядок работ читается в [роадмэпе](../roadmap.md#последовательность); у строки этапа должна быть прямая ссылка на его Issue, когда она создана. В самой Issue остаются зависимости и ссылки на источники, в Project — оперативный статус. Промежуточный PR закрывает рамочную Issue только если весь её заявленный объём принят; иначе он ссылается на неё без автоматического закрытия.

Перед созданием или обновлением описания проверить: модуль или этап назван в теле, ожидаемый результат понятен, ссылки ведут к нужным разделам, условия старта и сдачи не требуют угадывания. Если смысл задачи можно понять только после чтения всей концепции или истории обсуждения, описание нужно уточнить. Для реализации исполнитель всё равно читает указанные нормативные разделы.

Используется [компактный шаблон delivery Issue](templates/delivery-issue.md). Он задаёт форму описания, а не отдельную спецификацию или новый источник требований.

## Работа через gh

Операции с Issues, Pull Request и GitHub Project выполняются нативной утилитой `gh` с явным указанием репозитория или владельца, когда контекст неоднозначен.

Агентам запрещено выполнять команды `gh auth login`, `logout`, `refresh`, `switch` и `setup-git`, а также получать токен. Если текущей авторизации или scope недостаточно, агент останавливает только зависимую операцию и сообщает оператору точную причину.

После любой мутации GitHub агент выполняет отдельное чтение через `gh` и подтверждает фактическое состояние.
