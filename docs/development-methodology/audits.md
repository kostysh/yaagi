# Аудиты документов и кода

- Document ID: `project.methodology.audits`

Каждый проектный документ после создания или значимого изменения проходит аудит до merge. Значимым считается изменение смысла, границы, поведения, контракта, архитектурного решения, плана или обязательной проверки. Исправление опечатки или ссылки повторного аудита не требует.

## Выбор аудита

| Объект | Обязательный аудит | Основание |
| --- | --- | --- |
| Концепция и методология | `Concept Conformance Reviewer` | Принятые решения оператора, внутреннее отсутствие противоречий |
| Архитектура и ADR | `Concept Conformance Reviewer` | Каноническая концепция и вышестоящие решения |
| Дорожная карта реализации | `Spec Conformance Reviewer` | Каноническая концепция, принятая архитектура и решения оператора |
| Спецификация модуля | `Concept Conformance Reviewer` | Концепция и архитектура |
| План имплементации | `Spec Conformance Reviewer` | Архитектура и спецификация модуля |
| Описание алгоритма | `Spec Conformance Reviewer` | Спецификация модуля и применимые инварианты |
| Код | `Spec Conformance Reviewer` и `Security Reviewer` | Спецификация, план и обязательный security-аудит |

`Security Reviewer` дополнительно применяется к документу, если он вводит или меняет границу доверия, права доступа, работу с секретами или персональными данными.

## Проведение аудита

- Аудит всегда выполняет отдельный субагент. Агент, создавший или изменивший объект, не подменяет независимый аудит собственной проверкой.
- Субагент запускается на модели `gpt-6-astra` без форка контекста: `fork_turns: "none"`.
- Для локального объекта с ясными источниками используется reasoning `high`. Для концепции, архитектуры, нескольких связанных документов, границ доверия, неоднозначных источников или повторяющихся неудач используется `xhigh`.
- Субагент-аудитор работает только в режиме review и не исправляет проверяемые файлы.

Поскольку аудитор не получает историю диалога, запрашивающий агент передаёт ему самодостаточный пакет контекста:

- вид аудита и требуемый формат результата;
- точные пути проверяемых файлов и полный hash commit, являющегося базой аудита;
- scope и non-goals;
- источники истины, их приоритет и применимые решения оператора;
- проверяемый claim, критерии или ожидаемые инварианты;
- для повторного аудита — предыдущий отчёт, точную дельту и доказательства исправления.

Перед запуском аудита все проверяемые изменения коммитятся. Аудитору передаётся полный hash этого commit как неизменяемая база аудита; наличие commit не означает разрешения на push. Аудитор проверяет содержимое указанного commit, а не последующее состояние worktree. Один запуск может охватывать связанный набор документов, но результат должен явно показывать покрытие каждого файла.

## Результаты и отчёты

Для общей фиксации исходный verdict применённого review-skill сохраняется и дополнительно нормализуется:

- `PASS` — обязательных исправлений нет;
- `FAIL` — найден хотя бы один недостаток, который нужно исправить до завершения работы;
- `BLOCKED` — аудит нельзя завершить из-за отсутствующего или противоречивого контекста, источника либо снимка.

Каждый отрицательный результат (`FAIL`, `BLOCKED` или эквивалентный verdict с обязательным исправлением) фиксируется отдельным отчётом по [шаблону](templates/audit-report.md). Отчёт обязательно содержит полный hash проверенного commit и хранится по схеме:

`docs/validation/<module-id>/<task-id>.<scope-id>.<N>.md`

- `<module-id>` — стабильный смысловой идентификатор модуля; для общепроектных документов используется `project`;
- `<task-id>` — GitHub Issue в формате `gh-<issue-number>`;
- `<scope-id>` — `<artifact-scope>-<audit-kind>`, например `spec-concept`, `plan-spec` или `code-security`;
- `<N>` — последовательный номер отрицательного результата этого task и scope, начиная с `1`.

Идентификаторы должны быть пригодны для имени файла и не содержать `/`.

Один файл соответствует одной отрицательной попытке. Исходный снимок, verdict и findings не перезаписываются; после исправления в отчёт добавляются сведения о remediation и результате повторной проверки. Новый отрицательный результат получает новый файл со ссылкой на предыдущий.

Отчёт связывается с PR или Issue. Успешный результат можно зафиксировать кратко в PR или Issue без отдельного файла. Отчёты об отрицательных результатах являются входными данными для последующего ретроспективного анализа; они должны сохранять факты, причину решения и проверяемое доказательство, а не пересказ диалога агентов.

## Исправление и повторный аудит

Если аудит обнаружил недостатки, запрашивающий агент:

1. сопоставляет каждый принятый finding с источником, исправлением и проверкой;
2. исправляет весь прямой затронутый scope и выполняет применимые проверки;
3. коммитит исправления и получает новый полный hash commit;
4. передаёт результат тому же субагенту-аудитору;
5. явно поручает проверить только дельту: исправленные findings, прямой blast radius и отсутствие вызванных исправлением противоречий.

Пакет повторного аудита содержит предыдущий отчёт, полный hash прежнего audit commit, полный hash нового remediation commit, точную дельту между ними, доказательства исправления и обоснованные исключения. Неизменённая уже проверенная область повторно не исследуется. Если изменились исходный claim, источник истины или scope, это считается новым полным аудитом, а не delta re-audit.

## Три последовательных FAIL

Если один и тот же документ в рамках текущего изменения получает `FAIL` три раза подряд, агент прекращает цикл точечных исправлений и:

1. сообщает оператору о повторяющейся проблеме со ссылками на все три отчёта;
2. проводит более широкое исследование первопричины: проверяет вышестоящие источники, принятые решения, полноту контекста аудитора, повторяющиеся findings и прямые зависимости документа;
3. формулирует установленную или наиболее обоснованную первопричину и единый план исправления;
4. выполняет следующее исправление и delta re-audit только после этого исследования.

Третий `FAIL` не закрывается ещё одной локальной правкой без анализа причины. Результаты расширенного исследования добавляются в отчёт третьей попытки и используются в последующей ретроспективе.
