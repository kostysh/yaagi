# Методология разработки

Цель методологии — быстро превращать изменение замысла в проверенное поведение, сохраняя связь с концепцией и архитектурой. Процесс намеренно компактный: новый документ, этап или проверка добавляются только тогда, когда они устраняют текущую неоднозначность, защищают важное решение или позволяют безопасно распараллелить работу.

Базовый поток:

`Issue → task-worktree → task-ветка → имплементация и проверки → аудит → PR в develop`

## Основные правила

- Концепция, архитектура, спецификация модуля и план его имплементации — источники истины; Issues только связывают их с работой.
- Модули описываются через наблюдаемое поведение и BDD-сценарии, а не через классы и функции.
- Требования не детализируются глубже публичной границы модуля.
- Реализуется самая простая корректная версия без расширяемости «на будущее».
- Проверки и аудит соразмерны риску, но обязательные проверки не пропускаются ради скорости.
- Проектная документация ведётся на русском языке; английская создаётся по запросу оператора.
