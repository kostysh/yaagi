# Репозиторий, тесты и CI

## Структура репозитория

Проект организован как pnpm-монорепозиторий:

- рабочие пакеты размещаются в `packages/`;
- каждый пакет содержит собственные тесты;
- каждый пакет содержит конфигурации форматтера, линтера и typechecker;
- каждый пакет предоставляет scripts для локального запуска своих проверок;
- корневой `package.json` содержит агрегирующие команды, которые рекурсивно запускают package-level scripts средствами pnpm.

Корневые команды не должны содержать отдельную копию логики каждого пакета. Они только координируют одинаковые package-level команды.

## Автоматические проверки

Минимальный набор команд монорепозитория:

- форматирование и проверка форматирования;
- lint;
- typecheck;
- тесты.

Одни и те же команды используются локально и в CI. Версии package manager, инструментов и зависимостей фиксируются для воспроизводимости.

## Тестирование

Тесты выбираются по поведению и риску:

- unit-тесты — локальная логика;
- contract-тесты — публичные границы пакетов и модулей;
- integration-тесты — взаимодействие компонентов, хранилищ и внешних систем;
- BDD/acceptance-тесты — критические сценарии спецификации модуля;
- end-to-end — небольшое число критических сквозных путей;
- специализированные security, performance или resilience-тесты — когда риск этого требует.

Каждый исправленный дефект получает тест, воспроизводящий нарушенное поведение, если такой тест технически оправдан. Покрытие кода используется как сигнал, а не как самостоятельное доказательство качества.

## CI

CI разделяется на два обязательных уровня:

| Уровень | Назначение |
| --- | --- |
| PR | Быстрые format/lint/typecheck, сборка при её наличии и точные тесты затронутых пакетов |
| Merge | Полные проверки монорепозитория и необходимые интеграционные и сквозные тесты на merge-кандидате |

Дорогие проверки могут выполняться по расписанию или перед релизом, если они не нужны для каждого merge.

Оптимизация CI через кеширование, параллельное выполнение и выбор затронутых пакетов допустима, пока она не позволяет пропустить зависимый пакет или обязательную проверку. Flaky-тест не считается успешной проверкой и должен быть исправлен, а не скрыт retry.

Перед merge также выполняются [аудиты](audits.md), которые не заменяются зелёным CI.
