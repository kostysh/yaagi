## Источники и проверенный механизм

Оператор потребовал исполняемую нейтральную абстракцию со сменным adapter и отменил искусственный busy при пересечении независимых операций. Worker threads разрешены условно — после подтверждения корректности. Очередь/pool/scheduler/replay, lifecycle/exclusivity/process policy, другой driver/backend не добавляются.

Delta `5782f04251d2719b77f568842b461278874136f5` — Concept PASS. Все три reviewer: gpt-6-astra/xhigh, read-only, исходно fork-none; старый production scope не считался проверенным.

Диагностика DatabaseSync на главном потоке: первый writer удерживал transaction через await; второй BEGIN синхронно ожидал ~151 ms, блокировал continuation первого и получал native busy. Отдельный connection в том же JS-потоке не решал проблему.

[S1/S2 worker delta](../../../experiments/state/README.md#s1s2-delta-workers-и-native-concurrency-2026-09-29): отдельные threads/connections, native wait, awaited ORM/BLOB/vector writes, snapshot, rollback/cancel, bounded native timeout, close/reopen PASS. Первичный тестовый cleanup исправлен (reply до port.close); три последовательных изолированных прогона завершились без зависаний. Это причина принятия механизма, не throughput benchmark.

## Implementation self-check

- Root `createState(adapter, bind)` исполняет callback/Result/begin/finish и resource drain; ни SQL, ни Node/worker API в core/contracts. SQLite entrypoint только `/adapters/sqlite`; старые exports удалены. Breaking private 0.0.0 API, без aliases/new package.
- Каждый независимый вызов получает worker/connection; native SQLite координирует writers. RPC correlates сразу отправленные сообщения, Set учитывает ресурсы для close; нет app admission queue, pool, lock или replay. SQL и Drizzle внутри scope используют одну transaction.
- M1: `test/m1-consumer.ts` без изменений; один production core и одинаковые fixtures с двумя adapters/bindings. Memory double не заменяет SQLite acceptance.
- AbortSignal-совместимый переносимый signal включает abort events: одного snapshot boolean недостаточно для живой отмены в worker. Невалидная форма отвергается до I/O; structural non-Node signal и отмена выполняющегося SQL реально проверены. SQL не прерывается, cleanup дожидается завершения.
- Авария worker до/после COMMIT: safe unavailable, без ложного success или replay. При утрате ответа commit outcome может быть неизвестен; owner readback после reopen различает оба атомарных исхода. Не гарантируется rollback уже committed данных.
- Поля migrations/journal/SQL artifacts не менялись; rollback исходников и consumers на base не требует reverse migration файла.

Межпроцессные regression tests нашли ошибку первого переноса: metadata checks делали open/close существующих DB/WAL/SHM и снимали POSIX locks. Исправлено на lstat; O_EXCL создаёт только новый inode. [Объяснение SQLite](https://www.sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close), falsifier — реальный внешний writer, ожидание deadline, kill и reopen. После исправления PASS. Это сохранение нативных locks, не свой lock framework. Файлы принадлежат доверенному principal; hostile same-UID замена пути не sandbox-угроза, которую решает пакет.
