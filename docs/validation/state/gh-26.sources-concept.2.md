## Finding

### CC-STATE-002 — P2: опциональные policy limits не согласованы с обязательным архитектурным правилом

**Committed evidence:**

- `docs/architecture.md:274`: передача `AbortSignal` обязательна для отменяемого вызова.
- `docs/architecture.md:284`: cancellation и deadline обязательны для model/I/O/job; пределы принадлежат проверенной policy.
- `docs/modules/state/specification.md:48–57`: `signal`, `timeoutMs` и весь `OperationOptions` опциональны.
- `docs/modules/state/specification.md:63`: отсутствие `timeoutMs` явно означает отсутствие общего deadline.
- `docs/modules/state/specification.md:38,109`: предложение одновременно утверждает сохранение требований без ослабления гарантий.

Таким образом, точное предложение разрешает `readSnapshot`/`transact` без signal и без deadline, не устанавливая обязательную передачу policy limits вызывающим кодом и не выделяя разрешённое исключение из архитектуры. Формально соответствующая предложению реализация может завершить сколь угодно долгую операцию успешным commit без проверки какого-либо operation budget. Нынешние R/AC это не опровергают.

Это **не** требование прерывать синхронный SQL, добавлять worker/scheduler, контролировать агентский lifecycle или менять принятый драйвер. Ограничения cooperative cancellation в `specification.md:99,135` описаны честно. Finding касается отсутствия обязательного лимита, а не способности обеспечить hard wall-clock interruption.

**Минимальное исправление:** согласовать эту обязанность в источниках и точном предложении CP1. Либо контракт/правило вызова однозначно требует policy-derived cancellation/deadline для applicable I/O, либо CP1 явно выносит соответствующее исключение/изменение архитектурной гарантии на решение оператора. Не представлять последнее лишь как уточнение формы без изменения гарантий. Добавить соответствующий observable negative criterion.

Владелец исправления — `architecture-engineer` / `spec-engineer`; решения по изменению гарантии принадлежат оператору.

## Положительные результаты

Предложение поддерживает цель единой сохраняемой истории: общий transaction, consistent snapshot, owner-local схемы/revisions/DTO и одна композиционная migration chain. SQL/native handles не перемещаются в общий контракт; технический журнал не становится доменной моделью.

Новых обязанностей agent identity/admission/exclusivity/process management не найдено. `busy` одного соединения относится к конкуренции операций хранения, не к единственности агента.

Claim-relative классификация:

- **Будущая capability для owner adapters/root:** публичные гарантии чтения, общего commit и совместимости схем.
- **Substrate сейчас:** CP1 proposal и ограниченные экспериментальные механизмы.
- **Evidence:** реальные SQLite fixtures, fault/reopen и backup/readback; не production capability.

Просмотренный код содержит различающие oracle: mixed ORM/vector commit и rollback, конкурентный consistent snapshot, stale owner revision, expired handle, atomic migration failure, kill/reopen и backup с сохранением источника. Тестовая альтернатива M1 не выдаётся за durability-equivalent backend.
