# Дорожная карта реализации Полифонии

Дата: 2026-09-28. Основание: [концепция, §17](polyphony_concept.md#17-минимальная-живая-версия), [архитектура, §§2–10](architecture.md), [ADR](adr/), решения оператора о SQLite, сменных адаптерах `state`/`queue` и отсутствии Docker. Навигационная задача подготовки: [#16](https://github.com/kostysh/yaagi/issues/16).

Цель — первая живая версия со всеми обязательными способностями §17.1 концепции и наблюдаемым поведением §17.3. Порядок ниже охватывает 20 модулей кода, эксперименты E1–E3 и четыре точки интеграции из §8 архитектуры. **Текущий модуль — `core-types`.** Его первый инкремент предоставляет только compile-time тип `Result<T, E>`; IDs, refs, время, валидация и остальные части шага 1 ещё не реализованы. Эксперименты не начаты; мобильная и облачная поставки не входят в этот маршрут.

## Как пользоваться

Перед очередным модулем готовятся только его спецификация и компактный план по [методологии](development-methodology/modules.md). Требования и публичные контракты остаются в концепции, архитектуре и спецификациях; roadmap определяет последовательность. Общий меняющийся контракт согласуется до зависимой реализации. Проверка с двойником публичного порта позволяет работать независимо, но не закрывает сквозную приёмку.

Таблица задаёт основной последовательный маршрут. В колонке зависимостей указаны необходимые результаты, а не требование завершить каждый ранее перечисленный модуль целиком. Пакеты используют общие примитивы `core-types`; SQLite adapters владельцев дополнительно зависят от `state/sqlite`. В `state` и `queue` публичные контракты отделены от сменных адаптеров по [§2.4 архитектуры](architecture.md#24-адаптеры-state-и-queue); здесь реализуются desktop adapters. Первым потребителем `queue` становится `physiology`. Серверный пакет `infrastructure` исключён; будущие Expo/Cloudflare adapters сейчас не планируются.

`runtime` собирается постепенно: технический прототип I1, сквозной путь I2, автономный цикл I3, полная сборка и развитие I4. Это последовательные срезы одного модуля; его спецификация и план уточняются при расширении. Ранний срез проверяет только включённые реальные реализации и не считается готовой живой версией. Для I2 используются заданные тестовые режимы/бюджеты; динамическая регуляция добавляется в I3, governor и изменение навыков/органов — в I4. Допуск действий каждого среза требует завершённого E3 для его состава и адаптеров.

## Условия перехода

Подготовка окружения выполняется по мере необходимости: шаг 0 завершён, а шаг 1 начат и пока покрывает только проверенный `Result<T, E>`. Он остаётся незавершённым до реализации остальных требуемых общих примитивов. CI настраивается отдельной задачей перед merge или поставкой первого модуля по [политике качества](development-methodology/quality.md), SQLite/vector/queue dependencies — при реализации соответствующих adapters, целевое железо/model server — перед E1. Backup/restore проверяется до допуска реальных данных (§5.3 архитектуры). Реальные OS/filesystem/network границы проверяются перед использованием соответствующих adapters и workers; mock-проверка не выдаётся за sandbox. Queue consumer остаётся доверенным, isolated evaluator не получает SQLite/WAL/SHM/backup/lock или operator socket. Docker не требуется. Выбор Liteque закрывает отдельный ограниченный probe при работе над `queue`, не новый системный эксперимент.

E1–E3 возвращают измерения и ограничения в архитектуру. Провал эксперимента останавливает только зависимую реализацию или приёмку; меняющий архитектурное решение результат сначала разрешается на уровне архитектуры. Числа для тестовых сценариев не становятся рабочими лимитами без E2. Проверка I1 не закрывает E3. Результат E3 привязан к проверенным сборке, действиям и адаптерам: расширение среза не наследует допуск автоматически. После изменения transaction/recovery протокола затронутые проверки повторяются до допуска действий; на полной сборке E3 выполняется повторно перед I4.

Перед реализацией очередного модуля уточняется ближайшая строка, а после проверки результата — необходимые последующие зависимости. Подробные задачи остаются в плане модуля, статусы — в Issues. Каждый пакет проходит проверки и аудит по [методологии](development-methodology/README.md); общий контракт и его потребители интегрируются согласованно.

Поздними остаются мобильная/облачная поставки и Expo/Cloudflare adapters, дополнительные модельные семейства и аудио, модельный retrieval/RAG и reranking без измеренной пользы, дополнительные каналы связи, богатая семантическая/социальная модель, cloud consultants и somatic code evolution. Их отсутствие не исключает из первой версии минимальные world model, skills, physiology и Development Ledger. При включении расширения уточняются только затронутые контракты и границы по архитектуре.

Аудит roadmap проводится по концепции и принятой архитектуре через `spec-conformance-reviewer`; результаты и ограничения публикуются в связанной Issue или PR. Создание roadmap не является evidence выполнения экспериментов или работы организма.
