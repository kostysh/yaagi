# Дорожная карта реализации Полифонии

- Document ID: `project.roadmap`

Дата: 2026-09-30. Основание: [концепция, §17](polyphony_concept.md#17-минимальная-живая-версия), [архитектура, §§2–10](architecture.md), [ADR](adr/), решения оператора о SQLite, сменных адаптерах `state`/`queue`, использовании `state` для хранения очереди и отсутствии Docker. Навигационная задача подготовки: [#16](https://github.com/kostysh/yaagi/issues/16).

Цель — первая живая версия со всеми обязательными способностями §17.1 концепции и наблюдаемым поведением §17.3. Порядок охватывает 20 модулей, E1–E3 и четыре точки интеграции. По решению оператора 2026-09-30 разработка идёт на текущем хосте, модельные endpoints локальные или провайдерские и задаются через env вместе с интервалом тиков, с применением при restart. Модель/server сейчас не выбираются; server при необходимости поднимает оператор. Развёртывание самого runtime в облаке/mobile отложено, как и раньше; техническая изоляция планируется после работающей системы, backup/restore — для production.

## Как пользоваться

После принятия общего системного дизайна перед очередным модулем готовятся только его спецификация и компактный план по [методологии](development-methodology/modules.md). Требования, системные взаимодействия и публичные контракты принадлежат соответствующим уровням [иерархии документов](development-methodology/documentation.md#иерархия-источников-истины); roadmap определяет последовательность. Состав сборок и их проверяемый результат описаны в [§5 системного дизайна](system-design.md#5-поэтапная-сборка). Общий меняющийся контракт согласуется до зависимой реализации. Проверка с двойником публичного порта позволяет работать независимо, но не закрывает сквозную приёмку.

Таблица задаёт основной последовательный маршрут. В колонке зависимостей указаны необходимые результаты, а не требование завершить каждый ранее перечисленный модуль целиком. Пакеты используют общие примитивы `core-types`; SQLite adapters владельцев, включая mappings очереди, дополнительно зависят от `state/adapters/sqlite`. `queue` использует внедрённый публичный `StoragePort` готового `state` для отдельной технической БД; библиотека очереди подключается собственным сменным адаптером без отдельного DB-драйвера. Граница определена в [§2.4 архитектуры](architecture.md#24-адаптеры-state-и-queue). Первым потребителем `queue` становится `physiology`. Серверный пакет `infrastructure` исключён; будущие Expo/Cloudflare adapters сейчас не планируются.

`runtime` собирается постепенно: технический прототип I1, сквозной путь I2, автономный цикл I3, полная сборка и развитие I4. Это последовательные срезы одного модуля; его спецификация и план уточняются при расширении. Ранний срез проверяет только включённые реальные реализации и не считается готовой живой версией. Для I2 используются заданные тестовые режимы/бюджеты; динамическая регуляция добавляется в I3, governor и изменение навыков/органов — в I4. Допуск действий каждого среза требует завершённого E3 для его состава и адаптеров.

## Условия перехода

Подготовка окружения выполняется по мере необходимости: bootstrap завершён, `core-types` пока покрывает только проверенный `Result<T, E>`. CI и проверки перед поставкой следуют [политике качества](development-methodology/quality.md). SQLite/vector dependencies принадлежат `state`, Agenda 6.2.6 — проверенному adapter `queue`; эти пакеты не переоткрываются без несовместимости. Перед E1 оператор предоставляет модельную конфигурацию; приложение не устанавливает server. Runtime читает env при запуске, обеспечивает OS lock и ограниченный autorestart, не повторяет `unknown`. Техническая изоляция планируется после работающей Полифонии, эксплуатационные backup/restore — для production. Сейчас evaluator выполняет доверенный handler, API не передаёт ему storage/control ports и secrets; защита от скомпрометированного процесса не заявляется. Docker не требуется. Probe Agenda и storage-fault evidence не подменяют runtime E3.

E1–E3 возвращают измерения и ограничения в архитектуру. Провал эксперимента останавливает только зависимую реализацию или приёмку; меняющий архитектурное решение результат сначала разрешается на уровне архитектуры. Числа для тестовых сценариев не становятся рабочими лимитами без E2. Проверка I1 не закрывает E3. Результат E3 привязан к проверенным сборке, действиям и адаптерам: расширение среза не наследует допуск автоматически. После изменения transaction/recovery протокола затронутые проверки повторяются до допуска действий; на полной сборке E3 выполняется повторно перед I4.

Перед реализацией очередного модуля уточняется ближайшая строка, а после проверки результата — необходимые последующие зависимости и [сводка состояния](#состояние-разработки). Подробные задачи остаются в плане модуля, оперативные статусы задач — в Issues/Project. Каждый пакет проходит проверки и аудит по [методологии](development-methodology/README.md); общий контракт и его потребители интегрируются согласованно.

Поздними остаются мобильная/облачная поставки и Expo/Cloudflare adapters, дополнительные модельные семейства и аудио, модельный retrieval/RAG и reranking без измеренной пользы, дополнительные каналы связи, богатая семантическая/социальная модель, cloud consultants и somatic code evolution. Их отсутствие не исключает из первой версии минимальные world model, skills, physiology и Development Ledger. При включении расширения уточняются только затронутые контракты и границы по архитектуре.

Аудит roadmap проводится по концепции, принятой архитектуре, системному дизайну и решениям оператора через `spec-conformance-reviewer` по [правилам аудита](development-methodology/audits.md); результаты и ограничения публикуются в связанной Issue или PR. Создание roadmap не является evidence выполнения экспериментов или работы организма.
