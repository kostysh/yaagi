# Дорожная карта реализации Полифонии

Дата: 2026-09-25. Основание: [концепция, §17](polyphony_concept.md#17-минимальная-живая-версия), [архитектура, §§2–10](architecture.md), [ADR](adr/), принятое оператором уточнение `state` / BullMQ + Redis / `infrastructure`. Навигационная задача подготовки: [#16](https://github.com/kostysh/yaagi/issues/16).

Цель — первая живая версия со всеми обязательными способностями §17.1 концепции и наблюдаемым поведением §17.3. Порядок ниже охватывает 20 модулей кода, служебный пакет `infrastructure`, эксперименты E1–E3 и четыре точки интеграции из §8 архитектуры. **Следующий модуль — `core-types`.** Реализация модулей, Compose и эксперименты ещё не начаты.

## Как пользоваться

Перед очередным модулем готовятся только его спецификация и компактный план по [методологии](development-methodology/modules.md). Требования и публичные контракты остаются в концепции, архитектуре и спецификациях; roadmap определяет последовательность. Общий меняющийся контракт согласуется до зависимой реализации. Проверка с двойником публичного порта позволяет работать независимо, но не закрывает сквозную приёмку.

Таблица задаёт основной последовательный маршрут. В колонке зависимостей указаны необходимые результаты, а не требование завершить каждый ранее перечисленный модуль целиком. Пакеты кода используют общие примитивы `core-types`; собственные PostgreSQL adapters владельцев дополнительно зависят от `state/postgres`. `queue` инкапсулирует BullMQ/Redis, первым потребителем становится `physiology`. `infrastructure` обеспечивает серверы, не входит в граф импортов и не требует TypeScript API. Прототипы интеграции не считаются готовым `runtime`; окончательная сборка принимает реальные реализации через публичные границы.

## Условия перехода

Подготовка окружения выполняется по мере необходимости: сейчас выполнен только шаг 0; CI настраивается отдельной задачей перед поставкой первых модулей по [политике качества](development-methodology/quality.md), PostgreSQL/Redis — в `infrastructure` перед интеграцией `state`/`queue`, целевое железо/model server — перед E1. Backup/restore проверяется до допуска реальных данных (§5.3 архитектуры). Реальные OS/filesystem/network границы проверяются перед использованием соответствующих adapters и workers; mock-проверка не выдаётся за sandbox. BullMQ consumer остаётся доверенным, isolated evaluator не получает credentials PostgreSQL/Redis или Docker socket.

E1–E3 возвращают измерения и ограничения в архитектуру. Провал эксперимента останавливает только зависимую реализацию или приёмку; меняющий архитектурное решение результат сначала разрешается на уровне архитектуры. Числа для тестовых сценариев не становятся рабочими лимитами без E2. Проверка I1 не закрывает E3; после изменения transaction/recovery протокола затронутый эксперимент повторяется.

Перед реализацией очередного модуля уточняется ближайшая строка, а после проверки результата — необходимые последующие зависимости. Подробные задачи остаются в плане модуля, статусы — в Issues. Каждый пакет проходит проверки и аудит по [методологии](development-methodology/README.md); общий контракт и его потребители интегрируются согласованно.

Поздними остаются дополнительные модельные семейства и аудио, embeddings/reranking без измеренной пользы, дополнительные каналы связи, богатая семантическая/социальная модель, cloud consultants и somatic code evolution. Их отсутствие не исключает из первой версии минимальные world model, skills, physiology и Development Ledger. При включении расширения уточняются только затронутые контракты и границы по архитектуре.

Аудит roadmap проводится по концепции и принятой архитектуре через `spec-conformance-reviewer`; результаты и ограничения публикуются в связанной Issue или PR. Создание roadmap не является evidence выполнения экспериментов или работы организма.
