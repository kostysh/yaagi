# ADR-003: Границы действия, моделей и развития

- Document ID: `project.adr.003`
- Статус: accepted — решения оператора 2026-09-24/28; 2026-09-30 разрешены провайдерские env-профили и отложена техническая изоляция. Runtime enforcement ещё не реализован.
- Дата: 2026-09-30.
- Основание: [концепция](../polyphony_concept.md), §§4.10, 6.2.1, 7.2–7.6, 9.4, 11.2, 13–16; уточнение оператора 2026-09-24 о негенеративных и аудиомоделях.
- Связанный документ: [архитектура, §§2–4 и 6–10](../architecture.md).

## Контекст

Агенту нужны автономность, внимание к оператору и развитие, но ни одно из них не выдаёт неограниченные права на инструменты, память, host или изменение собственного тела. Модельные ответы, входные материалы и candidate code нельзя считать доверенным кодом runtime.

## Решение

`model-organs` — общая граница модельных вычислений разных модулей: генерация и дополнительные capabilities по потребности. Потребитель получает узкий `ModelPort` с типизированными входами/результатами и бюджетом. По решению 2026-09-30 модели используют OpenAI-совместимые запросы; AI SDK остаётся внутренним адаптером. Доменные контракты не содержат SDK/provider-объектов. Сначала одна конфигурация DEFAULT, дополнительные роли вводятся с потребителями; одновременные вычисления не создают второго decision loop.

Модель получает bounded контекст и возвращает проверяемый результат; API key используется только HTTP-транспортом, не prompt, job или журналом. DB writer и callback исполнения модели не передаются. Оператор задаёт URL/name/reasoning/api_key профилей через окружение при запуске/перезапуске; URL может быть локальным или провайдерским. Server при необходимости поднимает оператор. Контракт конфигурации, разделение секретов ролей и история при restart заданы в [§2.5 архитектуры](../architecture.md#25-конфигурация-моделей-и-интервала). Провайдер получает предназначенный ему контекст; приватность локального профиля не заявляется для удалённого. Endpoint из model/job input, неявный fallback и перенос Authorization на другой origin запрещены. Внешний консультант остаётся отдельной поздней ролью, а не названием любого провайдера.

Только executive принимает одно окончательное решение тика и вызывает описанный adapter после актуальной authorization. Policy/approval проверяет аргументы, principal, target hash/version и scope; невалидное или отсутствующее разрешение не допускает side effect. По решению 2026-09-30 OS sandbox/mount/network изоляция планируется после работающей Полифонии. Сейчас ограничения API и проверенного кода не выдаются за защиту от скомпрометированного процесса.

У Полифонии ровно один оператор; тот же человек общается с ней и управляет системой. Его доверенная привязка находится в `constitution`, а один локальный CLI использует один Unix socket с OS authentication. Операции общения и управления различаются явным типом запроса. Сообщение, включая просьбу одобрить развитие, остаётся стимулом и не является `ApproveChange`. Форма/время/необходимость ответа и инициативного обращения принадлежат общему циклу решений.

Чаты, browser use и социальные аккаунты могут добавляться позднее как каналы восприятия и действий. Они не создают новых операторов: внешние собеседники остаются собеседниками, а подтверждённые каналы оператора относятся к одному и тому же человеку. Текст, имя профиля и аккаунт самой Полифонии не устанавливают operator identity или полномочия управления.

Scheduler/evaluator — субперсональные процессы: они подготавливают данные и технические evidence, не меняют PSM, narrative, цели или active bindings. Результаты, включая оценки модели, привязаны к входному snapshot/hash и проходят проверку. Semantic change проходит следующий тик и governor.

`queue` использует SQLite через адаптеры [§2.4 архитектуры](../architecture.md#24-адаптеры-state-и-queue). Consumer и исполняемые handlers — доверенный проектный код. Evaluator получает snapshot/scratch через API без storage/control ports; это логическая граница, OS-изоляция отложена. Payload не выбирает исполняемый код. `physiology` проверяет admission, окно, бюджет, отмену и revision перед каждой попыткой и принимает результат по durable ID/hash. Повтор очереди не создаёт нового права действия, `unknown` остаётся в executive/reconcile. Смена adapters не расширяет полномочия consumer/evaluator.

Серверных БД и обязательного Docker нет. Каталог cell и файлы state/queue/WAL/SHM принадлежат доверенному principal и исключены из workspace API. SQLite не шифрует данные автоматически. Native `sqlite-vec` загружает доверенный adapter из фиксированной поставки, без пути/бинарника из model/job input. Секреты не попадают в payload, snapshot или логи. Отдельный worker-процесс сам по себе не является sandbox. Эксплуатационное резервное копирование планируется для production; готовые примитивы `state` сохраняются.

Платформенный вызов обработчика, включая будущий Expo background callback, даёт окно исполнения, но не authorization и не право нового subjective tick/внешнего эффекта. При возобновлении сохраняются проверки revision, admission и cancellation. Mobile/cloud lifecycle и изоляция требуют отдельного решения и evidence в целевом окружении; текущая поставка остаётся desktop.

Активируется только точная проверенная версия кандидата. Governor требует обоснования, проверки на новых случаях, continuity и rollback; freeze и policy перепроверяются перед применением. Смена базового органа и исполнимого навыка требует отдельного внешнего подтверждения. Стабильный body read-only; полноценная code evolution отложена, но её governance и recovery obligations сохранены.

Grant связывает canonical approval/evaluation с agentId, target scope, исходной active revision и hash кандидата. Он атомарно потребляется одним actionId; compare-and-swap защищает смену binding. Историческое чтение не восстанавливает executable authority, а изменённый payload того же requestId отклоняется. Повтор после rollback требует новой оценки/разрешения, recovery завершает только прежний action. Невозможность сохранить admission/grant-consumption запрещает side effect.

## Рассмотренные варианты

- **SDK agent владеет tools/memory/workflow:** связывает субъектность и эффекты с framework substrate, нарушая заменяемость и единый action boundary.
- **Operator message автоматически является operator command:** смешивает внимание, содержание и полномочия; концепция прямо разделяет их.
- **Worker применяет результат evaluation сам:** создаёт параллельный смысловой/исполнительный путь вне субъективного тика.
- **Self-improvement без внешних gates, потому что код локальный:** локальность не ограничивает доступ к credentials/host и не подтверждает безопасность candidate code.
- **Запрет всех изменений личности:** подменяет continuity неизменностью ценностей. Проверяется сохранность своего опыта и обязательных границ, а не постоянство предпочтений.

## Последствия и ограничения

Core и ранние evaluators содержат только доверенный review-approved код. Кандидаты навыков — данные/процедуры из разрешённых операций, модели — настроенные endpoints; произвольные generated code/dependencies не исполняются. Package boundaries не защищают от злонамеренной зависимости. После работающей версии планируются техническая изоляция и её реальные проверки; её отсутствие не отменяет проверку результатов и полномочий.

Отключение CLI не прекращает автономную работу. Недоступность обязательного endpoint, включая сеть провайдера, может остановить субъективные тики с явной причиной; история сохраняется. Offline-работа проверяется только для локального профиля, скрытой подмены модели нет.

Операторский control остаётся вне identity-bearing state. Политика может ограничить допустимое действие, но не задаёт агенту обязательный смысл жизни или биографическую интерпретацию события.

## Проверка и пересмотр

L2–L3, D1, S1–S3 и H1: operator content попадает в reasoning; control-команды не возникают из текста; действует одна доверенная привязка оператора, чужой OS principal не получает доступ к socket; evaluator inputs не содержат storage/control ports или credentials; model output не вызывает второй effect; неверный/устаревший/потреблённый grant отклоняется; conflicting replay не создаёт нового права; freeze блокирует promotion; rollback сохраняет ledger/episodes, навыки проверяются на новой модели. Защита от скомпрометированного evaluator остаётся будущим предметом проверки.

Для каждого настроенного endpoint проверяются формат запросов, reasoning, отказ/отмена, правильный профиль, redaction и отсутствие неявного fallback/перенаправления ключа. Для локального профиля дополнительно проверяется offline-работа. Для workspace adapter — path/symlink escape и secret exposure. OS/process/network проверки относятся к будущему этапу изоляции и не блокируют первый доверенный рабочий контур.

Для queue path S1/R4 сейчас проверяют состав evaluator inputs, запрет недоверенной загрузки extension, отказ неизвестному handler/conflicting payload, повторный admission при retry и невозможность повтором job вызвать новый внешний effect. Недоступность host files/socket скомпрометированному процессу не заявляется до будущей изоляции. Retention и повтор результата проверяются с owner receipt; Queue event не выдаёт разрешения и не становится каноническим доказательством выполнения.

M2 проверяет typed capability/input/output, неподдерживаемую операцию и общий бюджет; для каждого включённого адаптера требуется реальный вызов. Дополнительно проверяется, что модельная оценка не выдаёт права, а медиа не открывают произвольный filesystem/network доступ или воспроизведение вне executive. Эти обязательства применяются при включении соответствующей операции; перечисление семейства не доказывает его работу.

Новый внешний adapter, другой transport, cloud consultant, исполнимый skill с новыми правами или somatic pipeline требует пересмотра затронутой trust boundary до активации. До этого расширение не разрешается общими формулировками о развитии.
