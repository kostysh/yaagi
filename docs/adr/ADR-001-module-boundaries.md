# ADR-001: Независимые пакеты и единая сборка организма

- Document ID: `project.adr.001`
- Статус: accepted — принято оператором 2026-09-24, SQLite, переносимость и сменные адаптеры уточнены оператором 2026-09-28; реализация ещё отсутствует.
- Дата: 2026-09-28.
- Основание: [концепция](../polyphony_concept.md), §§2, 5.2, 7.6, 8.7, 12.2, 16.1–16.2.1; требования оператора о независимой разработке и сменных адаптерах `state`/`queue`.
- Связанный документ: [архитектура, §§2–4 и 8](../architecture.md).

## Контекст

Части Полифонии должны разрабатываться отдельно, но не становиться независимыми субъектами. В актуальном baseline нет runtime, поэтому совместимость с удалённой прежней реализацией не требуется. Общая память и executor задают ограничения на сборку, но не требуют общего mutable объекта или произвольного доступа к таблицам.

## Решение

Использовать pnpm-монорепозиторий с пакетами по способностям и одним composition root. Независимость означает возможность написать, собрать и проверить пакет против зафиксированных публичных контрактов без реализации соседей. Она не означает обязательные отдельный сервер, репозиторий или релиз каждого пакета.

Публичные DTO/validators принадлежат владельцу способности и экспортируются через `./contracts` без I/O. Implementations/adapters связываются root через явные порты. Общий `core-types` ограничен идентификаторами, ссылками на evidence и базовыми value/result types. Он не становится местом всех событий и состояния организма.

Направления зависимостей и владельцы state нормативно перечислены в архитектуре. Private/deep imports, обход владельцев через SQL и скрытая service-locator связность запрещены. Собственные SQLite adapters получают общий transaction handle, не права на произвольный доменный API. У каждого пакета свои проверки; contracts имеют самостоятельные fixtures.

`state` имеет нейтральный контракт транзакций, снимков и совместимости схем, реализуемый сменными адаптерами. SQLite-коннектор и технический export `state/sqlite` принадлежат локальному адаптеру; SQL, revisions, DTO/validators и миграции конкретного владельца остаются у него. Общие контракты не экспортируют SQL/драйверные типы. Замена СУБД требует новых adapters и миграции с сохранением прежних гарантий, а не изменения доменных контрактов или обещания универсального SQL. Уточнение оператора 2026-09-29: жизненный цикл и единственность инстанса агента принадлежат `runtime`, не `state`; механизм будет выбран при разработке runtime.

`queue` — общий технический модуль устойчивых именованных очередей. Контракт отделяет учёт задания от транспорта и возможности выполнять его сейчас; сменные адаптеры скрывают хранение, доставку и запуск обработчика. SQLite-файл и постоянный worker не входят в общий API; status/result и остальные гарантии сохраняются независимо от возможностей backend. Кандидат desktop backend — Liteque, окончательная фиксация зависит от проверки в §8 архитектуры. Первым потребителем служит `physiology`, которому принадлежат виды работ, admission, окна, бюджеты, intents/outbox и receipts. `queue` не импортирует `state` или потребителей; согласование с каноническим состоянием выполняет владелец задания по [протоколу хранения](ADR-002-state-and-recovery.md).

Для обоих модулей root явно связывает адаптеры с потребителями через общие порты. Ограничения backend учитываются явно, несовместимая реализация не принимается за совместимую по одним сигнатурам. Границы и проверка адаптеров определены в [§2.4 архитектуры](../architecture.md#24-адаптеры-state-и-queue). Будущие Expo/Cloudflare adapters не являются обязательством текущей поставки; конкретные API и устройство уточняются в спецификациях модулей.

Всего предусмотрены 20 пакетов кода. Серверных БД и обязательного Docker больше нет, поэтому `infrastructure` исключён из состава: пустая оболочка не нужна. Локальные файлы и соединения принадлежат `state`/`queue`, lifecycle сборки — `runtime`. Общие contracts/доменная логика не зависят от Node, SQLite driver, очередной библиотеки или Expo; platform adapters имеют отдельные entrypoints и подключаются в root. Будущая Expo-совместимость ограничивает контракт, но не добавляет мобильную реализацию, UI, сборку или mobile acceptance в первую поставку.

Изменение общей границы выполняется последовательно до распараллеливания потребителей. Breaking change включает согласованную contract version и обновление всех затронутых consumers. Совместимая замена implementation сохраняет доменный код потребителей, меняет root binding и проходит прежние contract/integration checks. Смена хранилища дополнительно может требовать новых storage adapters владельцев и миграции данных.

## Рассмотренные варианты

- **Микросервисы для каждого модуля:** усложняют единый commit, recovery и эксплуатацию; независимое развёртывание не запрошено. Model servers и isolated evaluators остаются процессами по своим реальным границам.
- **Один runtime с произвольными взаимными импортами:** прост в начале, но не позволяет независимо фиксировать и проверять модуль.
- **Общий пакет всех контрактов/состояния:** делает изменение любой способности изменением общей основы и размывает владение.
- **Универсальные плагины и runtime loading:** не нужны для текущих возможностей и расширяют поверхность исполнения недоверенного кода. Замена доменного пакета происходит при сборке/контролируемом restart.

## Последствия

- Независимые потоки начинаются после небольшой общей работы над контрактами; ранняя интеграция проверяет действительную совместимость.
- Package boundary не изолирует злонамеренный trusted-code dependency в одном Node-процессе. Кандидатный код и модели находятся вне core trust boundary; см. ADR-003.
- Новая способность требует обоснованного owner boundary, а не автоматического создания пакета для каждого понятия концепции.
- Решение не фиксирует внутренние классы, SQL-таблицы или алгоритмы владельца.

## Проверка и пересмотр

M1: пакет проходит собственные проверки с contracts/doubles, а затем две совместимые реализации проходят ту же интеграцию. Изменение private кода потребителя при замене означает нарушение границы. Статический граф и `exports` должны подтверждать объявленное направление зависимостей.

Для `state` проверяется отсутствие vendor types в общем контракте и участие owner adapters в одном commit; для `queue` — отсутствие backend/Node/Expo types у потребителя, собственные contract/restart проверки и работа с прерванным execution window. Общие exports не загружают native driver или Node-only код транзитивно. Реальные SQLite/vector/queue проверки нельзя закрыть двойниками портов; подтверждение запуска на смартфоне отложено.

Пересмотр требуется при подтверждённой потребности в независимом развёртывании/масштабировании либо если реальные invariants не удерживаются выбранным графом. Перед выделением сервиса повторно решить ownership, consistency и recovery. Пока runtime отсутствует, миграция существующих данных не применяется.
