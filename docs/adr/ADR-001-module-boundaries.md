# ADR-001: Независимые пакеты и единая сборка организма

- Статус: accepted — принято оператором 2026-09-24; реализация ещё отсутствует.
- Дата: 2026-09-23.
- Основание: [концепция](../polyphony_concept.md), §§2, 5.2, 7.6, 8.7, 12.2, 16.1–16.2.1; требование оператора о независимой разработке.
- Связанный документ: [архитектура, §§2–4 и 8](../architecture.md).

## Контекст

Части Полифонии должны разрабатываться отдельно, но не становиться независимыми субъектами. В актуальном baseline нет runtime, поэтому совместимость с удалённой прежней реализацией не требуется. Общая память и executor задают ограничения на сборку, но не требуют общего mutable объекта или произвольного доступа к таблицам.

## Решение

Использовать pnpm-монорепозиторий с пакетами по способностям и одним composition root. Независимость означает возможность написать, собрать и проверить пакет против зафиксированных публичных контрактов без реализации соседей. Она не означает обязательные отдельный сервер, репозиторий или релиз каждого пакета.

Публичные DTO/validators принадлежат владельцу способности и экспортируются через `./contracts` без I/O. Implementations/adapters связываются root через явные порты. Общий `core-types` ограничен идентификаторами, ссылками на evidence и базовыми value/result types. Он не становится местом всех событий и состояния организма.

Направления зависимостей и владельцы state нормативно перечислены в архитектуре. Private/deep imports, обход владельцев через SQL и скрытая service-locator связность запрещены. Собственные PostgreSQL adapters получают общий transaction handle, не права на произвольный доменный API. У каждого пакета свои проверки; contracts имеют самостоятельные fixtures.

Изменение общей границы выполняется последовательно до распараллеливания потребителей. Breaking change включает согласованную contract version и обновление всех затронутых consumers. Совместимая замена implementation требует только нового root binding и прохождения прежних contract/integration checks.

## Рассмотренные варианты

- **Микросервисы для каждого модуля:** усложняют единый commit, recovery и эксплуатацию; независимое развёртывание не запрошено. Model servers и isolated evaluators остаются процессами по своим реальным границам.
- **Один runtime с произвольными взаимными импортами:** прост в начале, но не позволяет независимо фиксировать и проверять модуль.
- **Общий пакет всех контрактов/состояния:** делает изменение любой способности изменением общей основы и размывает владение.
- **Универсальные плагины и runtime loading:** не нужны для текущих возможностей и расширяют поверхность исполнения недоверенного кода. Замена доменного пакета происходит при сборке/контролируемом restart.

## Последствия

- Независимые потоки начинаются после небольшой общей работы над контрактами; ранняя интеграция проверяет действительную совместимость.
- Package boundary не изолирует злонамеренный trusted-code dependency в одном Node-процессе. Кандидатный код и модели находятся вне core trust boundary; см. ADR-003.
- Новая способность требует обоснованного owner boundary, а не автоматического создания пакета для каждого понятия концепции.
- Решение не фиксирует внутренние классы, SQL-таблицы или алгоритмы владельца.

## Проверка и пересмотр

M1: пакет проходит собственные проверки с contracts/doubles, а затем две совместимые реализации проходят ту же интеграцию. Изменение private кода потребителя при замене означает нарушение границы. Статический граф и `exports` должны подтверждать объявленное направление зависимостей.

Пересмотр требуется при подтверждённой потребности в независимом развёртывании/масштабировании либо если реальные invariants не удерживаются выбранным графом. Перед выделением сервиса повторно решить ownership, consistency и recovery. Пока runtime отсутствует, миграция существующих данных не применяется.
